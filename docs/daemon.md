# Dewbow daemon

The Rust daemon combines the local management service and Codex runtime owner. It is compiled into the `dewbow` executable. The current version manages one local host through Web; remote enrollment, routing, MCP and external agent access are deferred.

## Ownership and interfaces

Codex is the durable source of conversations, messages, tool items and native execution status. Dewbow owns one `daemon.sqlite` per [state directory](operations.md#state-directory), its private local data directory for configuration, management storage, runtime ownership files and daemon diagnostics. All conversations managed through that directory share the database. It retains managed session bindings, frozen creation configuration, request fingerprints and delivery receipts, process ownership, and only the active or uncertain turn information required for recovery. Confirmed terminal turns are removed from durable management state atomically with clearing the active turn. Display metadata and native history are reconstructed rather than copied.

The existing Web uses same-origin `POST /api/<operation>` with `{result}` or `{error}` envelopes and the `v1` camelCase contracts. Operations include inventory, creation and connection, native history, content reads, sends, steering, questions, approvals and interruption. `GET /api/subscribeSessionUpdates` emits `snapshot`, `update` and `streamError` events. Management-event and native-item cursors remain independent; reconnect with committed positions. `/mcp` and agent bearer authorization are not provided.

All Web calls have operator authority. `dewbow web` authenticates to a separate loopback control endpoint with a credential from private local configuration and issues a 60-second, one-use browser ticket. Web removes the ticket fragment before exchanging it for an HttpOnly, SameSite=Strict cookie. Cookies expire after twelve hours and are revoked by logout or daemon exit. Persistent control credentials never enter browser storage. Host and Origin checks reject other origins; all production listeners bind to `127.0.0.1`.

## Native discovery and execution

Discovery combines native app-server metadata, read-only native databases, rollout metadata headers and read-only CLI inspection. Unix process/socket discovery and macOS writer-lock observations are retained where available. Unavailable providers report their state; a missing observation never proves another runtime is idle. Files must be owned by the current account and private paths reject links and Windows reparse points. Version-sensitive native database access is isolated in the Rust SDK.

The owned runtime excludes the launching Desktop conversation's executor and thread context. Native credentials and ordinary user configuration remain local to Codex. On Windows it uses the documented `features.prefer_mxc=true` preference, honoring native managed requirements and the native legacy fallback. This does not edit the user's Codex configuration. Devices without MXC still need a functioning permitted legacy sandbox; Dewbow does not disable sandbox boundaries or provision OS accounts automatically.

Reading inventory and history does not resume threads or start turns. Connect explicitly to continue an existing native ID. A writer conflict never causes Dewbow to stop another runtime. Managed creation freezes the selected model, effort, developer instructions and host-owned sandbox/approval policy. Session-specific arbitrary native configuration is not accepted.

One conversation permits one active or unresolved turn. Management operations and native notifications serialize state updates for that conversation, so a fast completion cannot be overwritten by a start response. Separate conversations can run independently. Default and Plan modes use the confirmed native model. Steering, interruption and interaction responses target exact native thread/turn/callback identities. Approval uses only the advertised single-request decision; no session policy amendment is applied. Unsupported callbacks remain visible with an interruption path.

Request IDs are durable within the selected state directory and remain effective across daemon restarts that reuse it. Claiming an ID is serialized across all conversations, independently of each conversation's execution gate. Repeating the same operation and input returns the original operation; different input with the same ID fails. Message bodies remain native or volatile; only their fingerprints are journaled. Delivery and native completion are separate. On restart, recorded conversations resume by ID under the same conversation gate as native notifications. A matching saved native turn confirms the original send receipt, and terminal native state clears its recovery record. A terminal notification also reconciles an uncertain send while the daemon is running. Unconfirmed delivery stays unknown and blocks another send; retry returns the original receipt without starting another turn. Old callbacks are invalidated because they belong to a terminated runtime. A native thread created before its ID was saved, or an empty thread that cannot resume, requires explicit recovery; Dewbow does not create a replacement silently.

History, activity and content reads never write management storage. Stateless content references identify a native item and an allowlisted output/diff selector, scoped to the conversation. Content reads resolve the native item through the SDK and return bounded UTF-8 byte ranges; raw reasoning is excluded. Historical output is exactly what Codex retained and can be truncated, so a nonempty terminal aggregate has unknown completeness. Dewbow does not archive complete command output independently.

Pending callbacks and their details/answers exist only in memory and are released when their turn ends. At most 64 callbacks are retained across the runtime, with details limited to 1 MiB each; additional callbacks are rejected rather than approved implicitly. Browser refresh can read them while the daemon lives; restart cannot replay them. Live content bridges native persistence delays in a buffer capped at 256 items and 16 MiB, with at most 1 MiB of appended text per item. Eviction may drop unpersisted live content. Management notifications use a 512-event memory buffer per session; they are not an audit log. A subscription identifies its daemon instance so Web can discard obsolete volatile events after restart.

## State and operations

Private configuration, process records, daemon diagnostics, the single management database and its WAL/SHM files belong to the selected state directory. It defaults to `~/.dewbow`; use the same `--state-dir <directory>` selection for initialization and subsequent management commands. Conversation working files use `workDir`, and native Codex data uses the configured Codex home. POSIX directories use mode 0700; Windows uses a protected ACL granting the current account and SYSTEM access, while preserving the directory owner. Privileged OS administrators remain outside this isolation boundary.

Back up state while stopped. Follow [management storage and compatibility](storage.md) for supported-format evolution and the selected [release's notes](release-notes/README.md) for upgrade sources or exceptional resets. Native credentials, conversations, working files and unrelated local results are preserved. Normal restart within the current valid format restores bindings and frozen configuration, then reads actual native state; an interrupted turn is not resumed as running merely because it was active at shutdown. Unknown schemas or malformed records stop startup before management writeback. See [CLI operations](cli.md) for setup and recovery.
