# Dewbow 0.2.0

Status: unreleased. The workspace development target is 0.2.0. These notes record the planned storage and upgrade boundary. Complete the product change list and release validation during release preparation; no 0.2.0 artifacts have been published.

## Changes

- Expose decentralized Network membership through CLI creation, invitations, exact-key local confirmation, joining, member/status reads, removal, self-exit and explicit contact configuration. Add retained join-result recovery and restricted departure delivery across restart and conflicting branches. Every member has the same membership authority; the founder can leave while others continue inviting peers. Reuse schema 2 and the existing management/key stores. No browser Network routes or remote native operations are added. See [Network CLI](../cli.md#network-membership).

- Add an independent Rust Network membership engine with strict signed-record validation, complete causal-history checks, compatible adoption proposals, exact-generation exit/readmission rules and synthetic conformance vectors. See the [engine integration contract](../network-membership-engine.md).
- Add the Network storage foundation: thirteen tables in the existing management database, per-admission protected keys, atomic invitation/join/exit/receipt operations and conservative recovery. See [Network storage](../storage.md#network-storage-foundation).
- Add authenticated direct Peer connections, membership proof bootstrap, bounded manifest/record reconciliation, signed contact hints, retry scheduling and shared result framing. Add `submitHistoryManifest` to carry the caller's paged ID manifest on its HTTP connection. Reuse schema 2 and existing key/settings/contact rows; optional peer attribution in the existing conflict reason retains quarantine across restart without changing the evidence JSON. Integrate upgrade maintenance and drain started work before shutdown releases ownership. Remote native access remains deferred. See [Peer transport](../network-peers.md).
- Use one live Dewbow management database per state directory. Retain conversation bindings, frozen creation configuration, request receipts and minimum recovery state. Read durable conversation history, command output and diffs from Codex instead of keeping a duplicate content/event archive.
- Establish a 24-hour minimum request deduplication window from server acceptance. Clean eligible older delivered/error receipts after startup recovery and once every 24 hours; retain accepted/unknown delivery and active execution/callback associations. Reusing a pruned request ID can execute new work. This bounded retry policy is part of the 0.2.0 compatibility baseline; it adds no request-expiry protocol, schema change or 0.1.0 migration. See [receipt retention](../storage.md#receipt-retention).
- Validate database versions, schema structure and persisted records before initialization or startup writeback. Preserve invalid or unknown state for recovery rather than silently resetting or stripping it. Keep absent native turn acknowledgements recoverable as unknown delivery.
- Add a native macOS Intel archive alongside the existing Linux x64, Windows x64 and macOS Apple Silicon targets.
- Replace operation-named Web endpoints with resource routes under `/api/v1`, GET reads, path-scoped mutations and retained operation receipt lookup. Update the bundled Web, SSE subscription and OpenAPI together. Preserve existing request fingerprints, deduplication retention and recovery records.
- Support local Windows validation through the same independent test host used in CI. Preserve the actual CI environment and same-account checks while running the complete Rust/npm and versioned upgrade suites outside a restrictive launcher's Job Object. Production handoff checks remain enforced.
- Exercise public-CLI version changes and injected download, worker, startup and duplicate-execution failures on all four native build targets before release artifact upload. The compatible synthetic predecessor is separate from the excluded 0.1.0 state transition.

## Compatibility boundary

This release establishes the preserving compatibility baseline. Migration from 0.1.0 is explicitly excluded for this one transition. Future supported releases follow the general [state-evolution policy](../../AGENTS.md#compatibility-and-state-evolution); this exception does not authorize later resets.

The published [0.1.0 release](https://github.com/rovewyn/dewbow/releases/tag/0.1.0) uses `daemon.sqlite` with `records` and `events`, plus `content.sqlite` with content tables. Its [tagged store](https://github.com/rovewyn/dewbow/blob/0.1.0/apps/daemon/src/store.rs) leaves `user_version` at SQLite's default `0`. This release uses one live `daemon.sqlite`, retains `records` and adds Network management tables under schema `2`. Earlier unpublished TypeScript state is also outside the supported import path.

The management API contract remains `v1`; the database advances independently to integer `2`. See [version identifiers](../storage.md#version-identifiers) for their separate purposes.

## Upgrade from supported schema 1 source builds

Valid source-build schema `1` state migrates to `2` without resetting the selected state directory. Stop the previous daemon and verify its owned native runtime has exited before replacing the executable. An older updater that requires target schema `1` cannot install this target automatically; use manual executable replacement and then start with the same state directory. Do not initialize a fresh directory for this supported transition.

Startup validates configuration, the exact source schema and every management record before write PRAGMAs. It checkpoints committed WAL content, writes a private `migration-backups/<backupId>/` database/configuration snapshot and hash manifest, verifies integrity, then adds the Network tables and advances `user_version` in one SQLite transaction before native startup or request admission. Interrupted migration leaves schema `1` intact and can be retried. Existing `records` JSON, host/session/native IDs, frozen configuration, request IDs/fingerprints, delivery receipts and uncertain recovery associations retain their values. Configuration is not rewritten and unjoined nodes generate no member key.

Restore an interrupted pre-commit upgrade only through its guarded transaction. After ordinary startup admits new work, a schema-1 executable cannot read schema `2`; manually restoring the pre-migration snapshot can discard new receipts or revive old authority. Stop and preserve current state, reconcile accepted work, and refuse rollback when those associations cannot be preserved. The inactive backup is recovery evidence, not permission for a later reset.

Private upgrade metadata advances to `v2` to inventory retained key files and source schema. The reader still supports original `v1` transactions, so a candidate migrating a sealed schema-1 snapshot can recover its predecessor. Public maintenance protocol `v1` is unchanged. Key-bearing snapshots are verified before restoration, and committed transactions cannot restore old state.

## HTTP API transition

This explicitly approved breaking HTTP transition removes all `/api/<operation>` routes and `/api/subscribeSessionUpdates`. No legacy aliases or redirects are provided. Clients must use the [resource routes](../interfaces.md#operations) under `/api/v1`, put identities in the path, send read options in the query and keep remaining mutation fields in the JSON body. Update external clients together with the daemon; refresh open Web tabs so they load the bundled client from the same installation. Authentication and private CLI control endpoints retain their paths and separate authority contracts.

The explicit version decision keeps the resource prefix `/api/v1`, OpenAPI version `v1` and existing `contractVersion: "v1"` payload marker for this coordinated replacement. The marker alone cannot distinguish the removed RPC transport from the resource transport. This is an approved one-time HTTP compatibility exception, not permission for future silent changes to `v1`.

Delivered session/turn creation returns 201, accepted delivery returns 202 and other operation receipts, including error/unknown, return 200. Mutation Location headers identify `/api/v1/operations/{commandId}`. Pre-receipt resource errors distinguish 409 conflicts, 429 capacity, 500 execution failures and 503 temporary unavailability. Native completion still requires observed turn state; delivery never establishes completion. Reads and SSE disable caching.

The HTTP adapter reconstructs the same domain names and inputs before fingerprinting. Existing state in the supported schema 1 format keeps its host/session identities, configuration snapshots, request receipts and recovery relationships. Retried requests must use the original path identities, requestId and remaining body; do not insert defaults or change frozen overrides. Receipt reads do not write state or extend retention. A missing/pruned receipt does not establish non-execution. This HTTP change requires no database migration or state reset.

Rolling back this HTTP change requires matching daemon and Web/client versions and another page refresh. The transport change does not itself change schema 1; the separate 0.1.0 storage rollback restrictions below still apply. Preserve uncertain delivery and reconcile it through the original request identity rather than replaying work.

## Upgrade from 0.1.0

The old binary has no built-in `upgrade` command or private upgrade maintenance protocol. Use the new release's installation instructions and a separate fresh Dewbow state directory:

1. Stop the old daemon using its selected state directory and verify its owned native runtime has exited.
2. Retain the old executable and private state as backups. Do not erase Codex home, credentials, conversations or working files.
3. Install the new executable and initialize a fresh directory with `dewbow --state-dir <fresh-directory> init --codex-executable <standalone-codex-executable>`. Use the same directory selection for later commands.
4. Run `doctor` and open Web using that selection. Select the intended Codex home explicitly at initialization when it differs from the default.

Fresh initialization creates a new host identity and independent management bindings, request receipts and recovery records. Old managed sessions are not imported. Native conversations remain available for explicit connection, but native history cannot reconstruct the old deduplication boundary. Inspect old uncertain operations before issuing new requests; a missing receipt in the fresh directory is not evidence that a native action did not happen.

## Rollback and release preparation

The single-database state cannot be used as a supported rollback path to 0.1.0. Retaining only the old executable is insufficient; any return to the old installation needs its original state, and activity accepted since the transition must be reconciled before retrying work.

The package declares state schema `2` and `rollbackSafe: false` for the unsupported 0.1.0 predecessor transition. The automatic updater rejects that policy before maintenance. Manual installation instructions above remain required; versioned synthetic acceptance uses a separate compatible archive and does not change the distribution policy. Product versions still identify the unreleased 0.2.0 development target. Preserve published tags and assets and publish the new release separately.

## Validation limits

Storage and lifecycle tests exercise synthetic schema-1/2 state, migration interruption, key publication/deletion recovery, admission expiry/send races, exact-generation exit acknowledgements, scoped receipts and guarded pre-commit rollback. Versioned acceptance retains the pinned predecessor's schema-1 storage and former HTTP transport, with an explicit synthetic coordinator overlay accepting target schema `2`. These checks do not demonstrate unmodified older-updater acceptance, 0.1.0 migration, real native acceptance on every platform or hardware power-loss safety. Complete release validation before publication.
